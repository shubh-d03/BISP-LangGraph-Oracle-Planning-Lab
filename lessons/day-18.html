The big idea

Long-running jobs usually return an identifier before their work has finished. Polling repeatedly checks a supported status endpoint at controlled intervals. The important outcomes are confirmed success, confirmed failure and uncertainty. A timeout or connection problem does not prove that the remote job failed or that it is safe to submit the write again.

If you are stuck writing the monitor, test it with a short list of fake status responses. It should stop as soon as a terminal result appears and should make no new submission call. Preserve the existing job identifier so the user can investigate an uncertain outcome.

day-18-example.py · Python
import time

def poll_job(get_status, job_id, max_attempts=10, delay=2):
    for _ in range(max_attempts):
        status = get_status(job_id)  # normalized: RUNNING/SUCCESS/FAILED
        if status in {"SUCCESS", "FAILED"}:
            return {"job_id": job_id, "status": status}
        time.sleep(delay)
    return {"job_id": job_id, "status": "UNKNOWN_TIMEOUT"}

# Timeout does NOT prove the job failed; do not auto-resubmit.
Explain this code
poll_job receives a normalized status provider and stops on SUCCESS or FAILED. It returns UNKNOWN_TIMEOUT when attempts are exhausted. Add explicit connection-error handling around the provider for the second exercise.
