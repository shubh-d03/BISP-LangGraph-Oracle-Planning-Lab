The big idea

Conversation memory lets an assistant reuse context across turns. A checkpointer stores graph state, and a thread identifier selects the conversation to continue. The same thread can remember a previous rule and Planning point of view. A different thread must remain independent. Memory is useful context, but it is not permission to repeat a prior write.

Open audio file

Follow the workflow

Start with Revenue Calculation for Forecast, September and fiscal year twenty-six. The user then says, now run it for October. In the same thread, update only Period and preserve the rule, Scenario and Year. Clear previous approval because this is a revised proposal. In a new thread, the same follow-up lacks context and needs clarification. The training in-memory checkpointer lasts only while its Python process remains alive; it is not durable storage across a restart.

Open audio file

If you are stuck

If you are stuck, check which thread identifier accompanies each invocation. Accidentally reusing one identifier for independent conversations can mix their context. Accidentally changing it during a follow-up can make context disappear. Test both situations with mocks. Compare the original and revised dictionaries, and verify that approval is cleared after a parameter change. Store useful request fields, not passwords, client sessions or unnecessary personal information.

02 / CLASS NOTES

Core concepts

Checkpointed state

Checkpointing persists graph state between invocations when the same thread ID is used.

Thread isolation

Different thread IDs must keep their own conversation context.

Named field updates

Follow-ups update named fields and reuse unspecified parameters.

Minimal stored context

Avoid storing passwords or unneeded personal data in conversational state.

Oracle Planning context. After a Forecast / Sep / FY26 rule request, the user says “Now run it for Oct.” Keep the rule and Scenario within that conversation.
