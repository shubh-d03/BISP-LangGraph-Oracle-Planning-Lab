The big idea

A reusable EPM client owns shared connection behavior, such as the base URL, authentication, timeouts and response parsing. Dedicated methods still handle different operations. This lesson also introduces a clear verification pattern for a substitution-variable update: read the existing value, make the approved change, then read it back in the same scope.

Open audio file

Follow the workflow

In the application-variable example, read Current Month, preview a change from August to September, perform the allowed update, and read it again. A matching read-back establishes that this target has the requested value. Now inspect the scope-mismatch case. If the update targets the Plan cube, an application-level read is not verification of that same target. Keep the application or cube scope explicit throughout the operation. Do not invent an asynchronous job identifier for an immediate update.

Open audio file

If you are stuck

If you are stuck organizing the client, move shared transport code once, then expose small operation-specific methods. A shared connection does not mean rules, integrations and pipelines all accept the same payload. For the variable exercise, record the order of fake-client calls: read, update, read. Confirm they use the same name and scope. A read-back mismatch must remain unverified rather than being presented as a successful change.

class EPMClient:
    def __init__(self, session, base_url):
        self.session = session
        self.base_url = base_url.rstrip("/")

    def get_json(self, verified_path):
        r = self.session.get(self.base_url + verified_path, timeout=30)
        r.raise_for_status()
        return r.json()

    # Add tested methods from Days 8–10 and a verified
    # substitution-variable read/update/read-back method.
