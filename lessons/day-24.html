The big idea

End-to-end testing checks behavior across the whole assistant. A tool working alone does not prove that clarification, conversation memory, approval and monitoring are connected correctly. This lesson follows a multi-turn Business Rule request, then changes its Period. The revised request must preserve useful context while clearing evidence and permission that belonged only to the earlier proposal.

Open audio file

Follow the workflow

The first request names Revenue Calculation but lacks its Planning point of view. A follow-up supplies Forecast, September and fiscal year twenty-six. The complete request is validated and reviewed before submission. The mock job then reaches a confirmed outcome. When the user says, now run it for October, preserve the rule and other members, but clear current validation, approval and job result. The successful September result stays separate. A rejected first proposal must make no write.

Open audio file

If you are stuck

If you are stuck, record intermediate state after every turn instead of looking only at the final sentence. Check the thread identifier, pending fields, exact approved parameters, write-call count and terminal job evidence. For the October follow-up, prove that no additional write happens before a fresh review. Include a failed-job case and verify that dependent steps are skipped. An understandable answer is useful, but the recorded transitions establish what the assistant actually did.

02 / CLASS NOTES

Core concepts

Integration behavior

Integration tests cover behavior across components, not isolated tool code alone.

Follow-up state

A follow-up should modify the requested parameter while preserving the rest.

Approval boundary

Approval must prevent writes before the user authorizes them.

Verified outcome

Job monitoring should surface final status, not merely submission.

Oracle Planning context. Run Revenue_Calculation, clarify Forecast / Sep / FY26, approve the proposal, verify the mock job, then change the Period to Oct.
