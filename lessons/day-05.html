The big idea

Conditional routing lets a workflow choose a path based on shared state. Instead of always running the same operation, the router inspects a field such as operation. A Business Rule request takes one path; a Pipeline request takes another. An unknown request has its own unsupported path. The goal is to make the decision explicit and testable, rather than letting unexpected input fall into a default write operation.

Follow the workflow

Change the operation in the lesson case selector. For a Business Rule, the router chooses the mock rule node. For a Pipeline, it chooses the mock pipeline node. Both keep the original Planning context, such as Forecast and September. An unlisted operation should reach the unsupported outcome and make no write. In Python, the routing function returns a route label, while the conditional-edge mapping identifies the actual graph node for that label.

If you are stuck

If you are stuck, write a small table before drawing the graph. Put each supported operation in one column and its destination node in the other. Add an unknown input and give it an explicit safe outcome. Test the routing function by itself with these values. Read the operation from the current state, not a global variable. Once the route labels are correct, connect them to nodes and inspect whether the original state fields are preserved.

02 / CLASS NOTES

Core concepts

Read shared state

Read request_type from graph state; do not depend on undeclared global variables.

Conditional edges

A conditional edge chooses a path based on a routing function.

Separate operation nodes

Separate tool-specific nodes make each operation testable.

Unsupported requests

Unknown requests should lead to a safe unsupported path rather than a random operation.

Oracle Planning context. Route a request to a mocked Business Rule or Pipeline. Keep Forecast / Sep / FY26 in shared state rather than global variables.
