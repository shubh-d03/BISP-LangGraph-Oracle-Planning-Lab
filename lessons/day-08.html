The big idea

This lesson automates deployed Oracle Planning Business Rules. A rule without runtime prompts needs its configured name. A rule with runtime prompts also needs the exact parameter names and valid member values defined for that rule. The returned job identifier is submission evidence, not proof of a completed calculation. Keep the function that submits a rule separate from the function that monitors its outcome.

Open audio file

Follow the workflow

Start with Revenue Calculation without runtime prompts and inspect the payload. Then switch to the runtime-prompt version for Forecast, September and fiscal year twenty-six. The demonstration uses the configured client to assemble the verified Planning Jobs request. In the browser lab, simulate an accepted request, an unauthorized response and an invalid prompt member. The accepted fixture is still processing. Save its identifier so a later monitor can check the terminal job status.

Open audio file

If you are stuck

If you are stuck on the exercise, compare the plain and prompted payloads. The plain request should not include an unnecessary parameters object. The prompted request must use the deployed rule's exact keys and members. Do not let a model invent them. Test with a fake client, inspect what it received, and check the submission response. If the page says Processing, do not summarize it as calculation completed. Monitoring is a separate responsibility.

    payload = {"jobType": "Rules", "jobName": rule_name}
